# firmware: what's in each folder

The program that runs on the nRF52840 DK board. It takes an EHG recording that the laptop streams in over the
serial port, releases it frame by frame on the board's own clock as if it were a live sensor, packs the samples into
numbered packets, and sends them to the laptop over Bluetooth.
Built on Zephyr (a small operating system for microcontrollers) via Nordic's nRF Connect SDK (NCS v3.4.1).
Setup notes and sources: [research/nrf-ble-environment.md](research/nrf-ble-environment.md).
Why the recording is streamed, not built in: [plans/realistic-injection-plan.md](plans/realistic-injection-plan.md).

## Whose is it? (ours vs Nordic's)

Everything on the board mixes **our code** with **Nordic's system** (the SDK: Zephyr operating system, Bluetooth radio software, build tools).
Our C code *calls* Nordic's functions (`bt_enable`, `k_sleep`, `LOG_INF`, …) but never contains them.

| Tag | Meaning | Files |
|---|---|---|
| **OURS** | written by us; this is the thesis work | `src/main.c`, `replay.c`, `ehg_service.c` + their `.h`, `ehg_packet.h`; `build.sh`; `tools/feed.py` (streams the recording in) |
| **OURS, fills in Nordic's form** | our file, but the format and setting names are Nordic's; we only choose the values | `ehg_node/prj.conf` (our values for Nordic's `CONFIG_…` settings), `ehg_node/CMakeLists.txt` (boilerplate + our file list), `ehg_node/Kconfig` (our 4 settings), `ehg_node/sysbuild.conf` (adds the MCUboot bootloader), `ehg_node/boards/nrf52840dk_nrf52840.overlay` (serial speed) |
| **GENERATED by Nordic's tools** | made by `west`/cmake/compiler on every build, not in git, safe to delete | everything in `build/` |
| **INSTALLED, outside the repo** | not our code, not in git; must be installed on the computer | the SDK `~/ncs/v3.4.1` (2.9 GB), the toolchain `/opt/nordic/ncs/toolchains/<id>/` (contains `west`, compiler, cmake, Python), `nrfutil` (`/opt/homebrew/bin`) |

Rule of thumb: if the file is in `src/`, we wrote it. If it is `build/`, Nordic's tools wrote it.
If it starts with `/opt` or `~/ncs`, Nordic installed it.

What our code takes from Nordic (the includes, by file):

| Our file | Nordic / Zephyr parts it uses |
|---|---|
| `main.c` | Bluetooth on + advertising (`bluetooth.h`, `conn.h`), chip ID (`hwinfo.h`), buttons + LEDs (`dk_buttons_and_leds.h`), timers and jobs (`kernel.h`), logging |
| `replay.c` | serial port with DMA (`uart.h`), byte queue (`ring_buffer.h`), CRC (`crc.h`), threads, clock ticks, queues (`kernel.h`), logging |
| `ehg_service.c` | Bluetooth data/command slots (`gatt.h`, `uuid.h`), byte-order helpers (`byteorder.h`), CRC, logging |
| `ehg_packet.h` | only small helpers (`util.h`, `toolchain.h`). The packet layout is entirely ours |

## src/ (the code)

| File | Role | Talks to |
|---|---|---|
| [`main.c`](../firmware/ehg_node/src/main.c) | start-up. Names the board `EHG-XXXX` from its chip ID, turns Bluetooth on, advertises, accepts the laptop's connection, Button 1 = start/stop, LED1 = connected, LED2 = sampling, logs link settings + counters every 10 s | [`ehg_service.c`](../firmware/ehg_node/src/ehg_service.c), [`replay.c`](../firmware/ehg_node/src/replay.c) |
| [`replay.c`](../firmware/ehg_node/src/replay.c) / [`.h`](../firmware/ehg_node/src/replay.h) | the sensor stand-in. Receives the recording from [`tools/feed.py`](../tools/feed.py) over the serial port into a queue (about 2 s ahead); on START releases 1 frame (1 sample per channel) at the recording's exact rate on the board's clock, stamps the tick, puts it in `replay_ring`. Answers clock pings, passes fault settings on | serial in, queue out |
| [`ehg_service.c`](../firmware/ehg_node/src/ehg_service.c) / [`.h`](../firmware/ehg_node/src/ehg_service.h) | takes frames from the queue, packs up to 10 per packet with a header, packet number and CRC, keeps a copy, sends over Bluetooth. Handles START / STOP / RESEND from the laptop. Fault injection stage (off unless asked). Keeps going while disconnected | queue in, laptop out |
| [`ehg_packet.h`](../firmware/ehg_node/src/ehg_packet.h) | byte layout of a packet (wire v2). Copy of [`gateway/packet.py`](../gateway/packet.py): change both together. Full table: [interface-spec.md §3](interface-spec.md) | used by both above |

How one frame travels:

```
data/converted/*.npz --(tools/feed.py, serial 460800, ~2 s ahead)--> feed_q on the board
  --(replay.c: board timer, 20/s, clock-stamped)--> queue "replay_ring" (256 frames)
  --(ehg_service.c: 10 frames + 20-byte header + CRC)--> history copy + Bluetooth message --> laptop (gateway/gateway.py)
laptop --(START / STOP / RESEND over Bluetooth)--> ehg_service.c
```

Threads (jobs that run side by side; lower number = more urgent):

| Thread | Priority | Does |
|---|---|---|
| replay thread ([`replay.c`](../firmware/ehg_node/src/replay.c)) | 2 | timing-critical: releases frames on time |
| serial parser ([`replay.c`](../firmware/ehg_node/src/replay.c)) | 4 | turns serial bytes into messages, fills `feed_q`, reports `@LVL` once a second |
| tx_thread ([`ehg_service.c`](../firmware/ehg_node/src/ehg_service.c)) | 5 | builds and sends packets, handles resends |
| main ([`main.c`](../firmware/ehg_node/src/main.c)) | 0 (Zephyr's default) | start-up, then LEDs every 200 ms and counters every 10 s. Most urgent, but asleep almost all the time |

## What happens, in order

From an empty board to packets arriving on the laptop, then on to a reconnect. **Who** acts at each step:
💻 a tool on the laptop, 🔧 Nordic/Zephyr, ✍️ our code. **You see** = where to look to check it happened.

Two things that are easy to get wrong:
- **The board never starts the Bluetooth connection.** `main.c` turns Bluetooth on and *advertises* ("I'm here").
  The laptop's `gateway/gateway.py` finds it and *connects*. `main.c` only accepts and reacts in callbacks.
- **`build.sh` installs the program; it does not start a recording.** The program is built and flashed once (like a
  factory install). A recording is then streamed in by `tools/feed.py`, and sampling starts with START (laptop) or Button 1.

A normal run, in order (Stages B–C once; Stage D every run):

```
firmware/build.sh flash                                          # B + C: build, flash, board boots and advertises
uv run python tools/feed.py data/converted/tpehgdb/tpehg1007.npz # D5-D7: stream the recording in (leave running)
uv run python -m gateway.gateway                                 # D8-D19: connect, START, receive (Terminal.app: Bluetooth permission)
```

### Stage A: prepare the recording (once per database)

| # | Who | What happens | You see |
|---|---|---|---|
| A1 | 💻 [`tools/convert.py`](../tools/convert.py) | PhysioNet `.hea/.dat` → `data/converted/tpehgdb/tpehg1007.npz` (raw counts, row 0 = `1093 171 -748`) | the `.npz` file + `manifest.json` |

### Stage B: build (`firmware/build.sh`, once per code change)

| # | Who | What happens | You see |
|---|---|---|---|
| B1 | ✍️ [`build.sh`](../firmware/build.sh) | makes the `~/thesisb` shortcut if missing | |
| B2 | 🔧 `nrfutil toolchain-manager launch -- west build` | starts Nordic's build tool inside Nordic's toolchain (`west` is not on PATH) | build log scrolling |
| B3 | 🔧 sysbuild reads [`sysbuild.conf`](../firmware/ehg_node/sysbuild.conf) | builds 2 programs: MCUboot (bootloader) and our app | `mcuboot` and `ehg_node` in the log |
| B4 | 🔧 CMake reads [`CMakeLists.txt`](../firmware/ehg_node/CMakeLists.txt) | finds Zephyr, gets the file list `main.c replay.c ehg_service.c` | `-- Found Zephyr` … |
| B5 | 🔧 Kconfig | merges Zephyr defaults + [`prj.conf`](../firmware/ehg_node/prj.conf) + our [`Kconfig`](../firmware/ehg_node/Kconfig) → `build/ehg_node/zephyr/.config` | e.g. `CONFIG_EHG_FRAMES_PER_PACKET=10` in `.config` |
| B6 | 🔧 devicetree | board file for `nrf52840dk/nrf52840` + our overlay → `zephyr.dts` (pins, radio, serial 460800, 1 MB flash, 256 KB RAM) | `zephyr.dts` |
| B7 | 🔧 GCC (`arm-zephyr-eabi-gcc`) | compiles our 3 `.c` files + Zephyr + the Bluetooth stack + MCUmgr, then links them into one program | `Memory region … FLASH … RAM …` |
| B8 | 🔧 | writes the images: the bootloader, the signed app, and the signed app packed for over-the-air updates | `build/mcuboot/zephyr/zephyr.hex`, `build/ehg_node/zephyr/zephyr.signed.hex`, `build/dfu_application.zip` |
| B9 | ✍️ `build.sh` | copies `compile_commands.json` with real paths for VS Code (see build/ table) | `build/compile_commands.json` |

### Stage C: flash + boot (`firmware/build.sh flash`)

| # | Who | What happens | You see |
|---|---|---|---|
| C1 | 🔧 `west flash --dev-id 1050208294` → `nrfutil` | writes the bootloader, then the signed app, into the nRF52840's flash through the DK's on-board USB debugger, then resets the chip | `Programming image` (twice), `Reset` |
| C2 | 🔧 MCUboot | checks the app's signature, then starts it (or a newly uploaded one, Stage F) | a burst of unreadable bytes on the serial port while the chip resets (harmless) |
| C3 | 🔧 Zephyr boot | sets up memory, clock (32768 ticks/s), drivers, logging | serial: `*** Booting nRF Connect SDK … ***` |
| C4 | 🔧 Zephyr | creates our 3 threads (`K_THREAD_DEFINE`) **before `main()` runs**: replay (priority 2), serial parser (4), tx (5). They run whenever `main` is waiting | nothing yet |
| C5 | ✍️ serial parser | starts DMA receive on the serial port (RTS/CTS on: the board can pause the laptop instead of losing bytes); waits for the laptop's CONFIG | nothing (no `@LVL` before CONFIG) |
| C6 | ✍️ replay thread / tx_thread | replay waits for START; tx checks for RESENDs and waits for frames | nothing |
| C7 | 🔧 Zephyr | registers our Bluetooth service (`BT_GATT_SERVICE_DEFINE`), the update service (MCUmgr/SMP) and the connection callbacks; all built in at compile time | nothing |

### Stage D: `main()` → feeder → connect → stream

| # | Who | What happens | You see (board log via feed.py / laptop) |
|---|---|---|---|
| D1 | ✍️ `main()` | reads the chip ID, names the board from its last 2 bytes | name `EHG-93C0` |
| D2 | ✍️ → 🔧 `bt_enable(NULL)` | turns the radio and Bluetooth stack on (waits until ready) | `<inf> bt_hci_core: …` lines |
| D3 | ✍️ `adv_work_handler` → 🔧 `bt_le_adv_start` | board broadcasts its name + EHG service ID every 100–150 ms | `<inf> main: advertising as EHG-93C0` |
| D4 | ✍️ `main()` | forever: LEDs every 200 ms, counters every 10 s | every 10 s: `<inf> ehg_svc: sent=0 offline=0 …` |
| D5 | 💻 [`tools/feed.py`](../tools/feed.py) → ✍️ `on_config` | opens the serial port, sends CONFIG (3 ch, 20 Hz, record 0, 16-bit, random session no.) every 0.5 s until answered. A repeat with the same session no. is only re-answered; a new feeder (new no.) empties the board's queue | `board EHG-93C0 ready` (from `@HELLO … #crc`) |
| D6 | 💻 feed.py → ✍️ `ehg_service_set_faults` | sends FAULT: all zero = off, or the `--faults` settings (Gilbert loss, corruption, forced disconnects; [fault-injection.md](fault-injection.md)). Logs the run in `eval/results/runs_EHG-93C0.csv` | `<inf> ehg_svc: faults: seed 1, good->bad …` |
| D7 | 💻 feed.py → ✍️ serial parser | streams DATA (10 frames per message) until 2 s are queued, then tops up once a second from `@LVL`; pings the clock once a second (`@SYNC`). Every `@` line carries a CRC, so a line damaged on the VCOM is ignored | `eval/results/sync_EHG-93C0.csv` grows |
| D8 | 💻 [`gateway.py`](../gateway/gateway.py) `ble_main` | `BleakScanner` lists nearby devices, picks names starting `EHG-` | laptop: `scanning for up to 1 node(s) named EHG-* ...` |
| D9 | 💻 `run_ble_node` → 🔧 | **the laptop connects** to the board | laptop: `[EHG-93C0] connected, mtu=247` |
| D10 | ✍️ `connected()` | stores the connection, asks for 2M PHY + max data length (requests only); LED1 on | `<inf> main: connected` |
| D11 | 🔧 → ✍️ `phy_updated`, `data_len_updated`, `mtu_updated` | the laptop answers; the callbacks only log what it granted | `PHY: tx 2 rx 2`, `data length: tx 251 B rx 251 B`, `ATT MTU: tx 247 rx 247` |
| D12 | 🔧 Zephyr (auto, ~5 s after connecting) | asks for the `prj.conf` connection interval (15–30 ms); macOS picks | `conn params: interval 30.00 ms, latency 0, timeout 6000 ms` |
| D13 | 💻 `start_notify(DATA_UUID)` | laptop flips the CCC switch: "send me notifications" | |
| D14 | 💻 writes `01` (or Button 1) → ✍️ `ctrl_write` → `replay_start` | numbers the session from the oldest queued frame, notes `t0`, wakes the replay thread; LED2 on. Ignored if already running; refused before CONFIG (start feed.py first) | `<inf> replay: replay start: record 0, 3 ch @ 20 Hz, from frame 0` |
| D15 | ✍️ replay thread | every 50 ms: sleep until due, **stamp the tick (= t_inject, where H1 latency starts)**, take that frame from `feed_q`, put `{tick, frame_idx, 1093 171 -748}` in `replay_ring`. Not there yet → skipped, `starved`; arrived too late → thrown away, `late` | `max_inject_late` in the 10 s line |
| D16 | ✍️ `tx_thread` | after 10 frames (fewer if many channels; closed early if a frame was skipped): 20-byte header + 60 bytes samples + 2-byte CRC, copy into history, `send()` → fault stage (off by default) → `bt_gatt_notify` | `sent=` climbs by 2 per second |
| D17 | 💻 `Node.on_bytes` | check CRC (mismatch → dropped, `bad=`; the next packet then shows it as a gap), decode, CSV line, gap check, publish JSON to MQTT `ehg/EHG-93C0/pkt` | `gateway/logs/EHG-93C0.csv` grows |
| D18 | 💻 → ✍️ (only on a gap) | laptop writes `03 <seq> <count>`; `ctrl_write` queues it, `serve_resends` re-sends from history with flags bit0 = 1. Still missing 1 s later (the copy was lost too) → asked again, up to 5 times | `resent=` / `resend_miss=` |
| D19 | 💻 backend → [`eval/`](../eval) | ingest stores each frame in InfluxDB (`t_db_ack` = H1 end point); `integrity.py` checks delivery + bit-exactness, `latency.py` maps board ticks to laptop time with the `@SYNC` pings | delivery %, mismatches, latency median/p95 |

### Stage E: disconnect / reconnect / stop

| # | Who | What happens | You see |
|---|---|---|---|
| E1 | 🔧 link lost (distance, `disc=` fault, laptop) | ✍️ `disconnected()` forgets the connection; **sampling continues**; packets made now go to history (`offline=`); LED1 off | `<inf> main: disconnected (0x08 / 0x13 / 0x16)` |
| E2 | ✍️ `recycled()` | once Zephyr has freed the connection: advertise again (back to D3) | `<inf> main: advertising as EHG-93C0` |
| E3 | 💻 gateway (still running) | reconnects after 2 s with the **same** gap tracker; START is a no-op; the first new packet shows the seq jump → RESEND for the outage (re-asked if a copy is lost) | laptop: `streams=1`; board: `resent=` jumps |
| E4 | 💻 Ctrl-C on the gateway, or Button 1 | STOP (`02`) → `replay_stop`; LED2 off. A later START begins a new session (seq from 0, history cleared) | |

An outage longer than the history (256 packets = 128 s at 20 Hz) loses its oldest packets: counted `resend_miss`,
listed by `eval/integrity.py`, never silent. The board keeps its program after power-off; unplug/replug = start
again from C2, and `feed.py` notices (no `@LVL` for 3 s) and sends CONFIG again.

### Stage F: update the firmware over Bluetooth (no cable)

| # | Who | What happens | You see |
|---|---|---|---|
| F1 | 💻 `firmware/build.sh` | builds as usual; the signed app is `build/dfu_application.zip` | |
| F2 | 💻 Nordic's **nRF Device Manager** phone app (iOS/Android) | connect to `EHG-93C0`, *Upload* the zip, choose *Test and confirm* | progress bar |
| F3 | 🔧 MCUboot (after the board resets) | swaps the new app in and starts it; if it doesn't confirm itself, the next reset goes back to the old one | serial: `*** Booting MCUboot … ***` then the new app |

`nrfutil mcu-manager ble` also exists but needs a second Nordic board as its Bluetooth radio, so the phone app is
the one-board route.

## Settings (Kconfig, change in prj.conf)

| Setting | Default | Meaning |
|---|---|---|
| `CONFIG_EHG_FRAMES_PER_PACKET` | 10 | frames per packet (fewer if many channels: max 244 B). More = fewer packets, more waiting (10 = 0.5 s at 20 Hz) |
| `CONFIG_EHG_RING_FRAMES` | 256 | queue between replay and sender (12.8 s at 20 Hz). Full = frames dropped + counted |
| `CONFIG_EHG_FEED_BUFFER_FRAMES` | 512 | frames the laptop can send ahead (feed.py keeps ~2 s; 512 covers 2 s at 200 Hz) |
| `CONFIG_EHG_HISTORY_PACKETS` | 256 | sent packets kept for resends (128 s at 20 Hz) |

Channels, rate, record_id and sample width (16 or 24-bit) are not build settings: the laptop sends them in CONFIG.

## The serial port (VCOM0, 460800 baud)

One port, two directions: the recording goes in (binary, from `tools/feed.py`, [interface-spec.md §3b](interface-spec.md)),
the log comes out. RTS/CTS flow control is on (the DK wires both to the J-Link chip), so the board pauses the
laptop instead of losing bytes while Bluetooth keeps the CPU busy. `feed.py` prints the log, so nothing else (screen, nRF Terminal) can have the port open meanwhile.

Every 10 s: `sent=… offline=… resent=… resend_miss=… notify_err=… ring_overflow=… starved=… late=… rx_bad=… max_inject_late=… us`
(+ `injected: drop=… corrupt=… disc=…` when faults are on, [fault-injection.md](fault-injection.md))

| Counter | Meaning |
|---|---|
| `sent` | packets sent (fault-dropped ones count as sent, as a real radio loss would) |
| `offline` | packets made while disconnected (kept in history, re-sent on request) |
| `resent` | packets sent again on request |
| `resend_miss` | resend asked for too late (copy already overwritten) = lost for good |
| `notify_err` | send failed (e.g. laptop connected but not listening yet, link going down) |
| `ring_overflow` | frames dropped because the queue was full (sending fell behind) |
| `starved` | frames the laptop had not delivered by their due time (skipped; test-rig loss, not radio loss) |
| `late` | frames that arrived after their due time (thrown away) |
| `rx_bad` | serial messages rejected (bad CRC/COBS/length, before CONFIG, queue full); each also logs a `<wrn>` with the reason |
| `max_inject_late` | worst lateness of any frame vs its exact due time |

## build/ (generated, not in git)

Made by [`build.sh`](../firmware/build.sh). Safe to delete; the next build remakes it (`build.sh pristine` does a clean build).
Most of it is build-tool internals. The parts worth knowing:

| Item | What |
|---|---|

| `build/dfu_application.zip` | the signed app alone, for an update over Bluetooth (Stage F) |
| `build/ehg_node/zephyr/zephyr.elf` | the app + debug info (for a debugger) |

## Glossary

| Term | Meaning |
|---|---|
| Zephyr | small operating system for microcontrollers: threads, timers, Bluetooth stack |
| thread | a job that runs side by side with others |
| queue / ring buffer | fixed-size waiting line between 2 threads |
| tick | 1 step of the board clock: 32768 per second |
| peripheral / central | board = peripheral (advertises, waits); laptop = central (connects) |
| advertising | board broadcasting "I'm here" so the laptop can find it |
| service / characteristic | a named group of data "slots" on the board. Ours: data slot (board → laptop) + command slot (laptop → board) |
| notify | board pushes data to the laptop without being asked each time |
| CCC | switch the laptop flips to say "send me notifications" |
| MTU | biggest message the link allows (247 bytes here) |
| PHY | radio speed mode (2M = 2 Mbit/s) |
| connection interval | how often board and laptop talk (15–30 ms here) |
| CRC | a 2-byte checksum; if any bit changes on the way, it no longer matches |
| COBS | a way to write a message without any 0x00 byte, so 0x00 can mark where each message ends |
| DMA | the serial hardware writes received bytes straight into memory, without the CPU |
| MCUboot / MCUmgr / SMP | bootloader that can swap in a new app / the service + protocol that uploads it |
| prj.conf / Kconfig | build-time settings / our own settings definitions |
| devicetree (`.dts`) / overlay | text description of the board's hardware / our changes to it |
| flash | copy the firmware image onto the board |
| west / nrfutil | Nordic's build and flash tools |
