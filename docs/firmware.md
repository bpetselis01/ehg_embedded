# firmware: what's in each folder

The program that runs on the nRF52840 DK board. It plays a stored EHG recording as if it were a live
sensor, packs the samples into numbered packets, and sends them to the laptop over Bluetooth.
Built on Zephyr (a small operating system for microcontrollers) via Nordic's nRF Connect SDK (NCS v3.4.1).
Setup notes and sources: [research/nrf-ble-environment.md](research/nrf-ble-environment.md).

## The folder

```
firmware/
  build.sh               1 command: build (+ flash) the board
  ehg_node/              the board's program ("app")
    CMakeLists.txt       which C files to compile
    prj.conf             Zephyr / Bluetooth settings
    Kconfig              our own settings (packet size, buffer sizes)
    src/                 the C code (below)
    build/               generated by the build. Not in git (below)
```

| Item | What |
|---|---|
| [`build.sh`](../firmware/build.sh) | build: [`firmware/build.sh`](../firmware/build.sh); build + flash: `firmware/build.sh flash`. Builds via `~/thesisb` because Nordic's build breaks on folder names with spaces |
| [`ehg_node/CMakeLists.txt`](../firmware/ehg_node/CMakeLists.txt) | lists the 3 C files; stops the build if `src/replay_data.h` is missing |
| [`ehg_node/prj.conf`](../firmware/ehg_node/prj.conf) | turns on Bluetooth + logging; sets message size (up to 244 B of packet), send buffers, how often board and laptop talk (15–30 ms) |
| [`ehg_node/Kconfig`](../firmware/ehg_node/Kconfig) | our 3 settings (table below) |
| `xiao_blinky` (repo root) | not part of the pipeline: a shortcut to a separate LED-blink test app (Seeed XIAO board), used once to check the toolchain worked |

## src/ (the code)

| File | Role | Talks to |
|---|---|---|
| [`main.c`](../firmware/ehg_node/src/main.c) | start-up. Names the board `EHG-XXXX` from its chip ID, turns Bluetooth on, advertises, accepts the laptop's connection, logs link settings + counters every 10 s | [`ehg_service.c`](../firmware/ehg_node/src/ehg_service.c) |
| [`replay.c`](../firmware/ehg_node/src/replay.c) / [`.h`](../firmware/ehg_node/src/replay.h) | the fake sensor. On START, releases 1 frame (1 sample per channel) at the recording's exact rate (20/s for TPEHG), stamps the board clock, puts it in a queue. Loops the recording | `replay_data.h` in, queue out |
| [`ehg_service.c`](../firmware/ehg_node/src/ehg_service.c) / [`.h`](../firmware/ehg_node/src/ehg_service.h) | takes frames from the queue, packs 10 per packet with a header + packet number, keeps a copy, sends over Bluetooth. Handles START / STOP / RESEND commands from the laptop | queue in, laptop out |
| [`ehg_packet.h`](../firmware/ehg_node/src/ehg_packet.h) | byte layout of a packet. Copy of [`gateway/packet.py`](../gateway/packet.py): change both together. Full table: [interface-spec.md §3](interface-spec.md) | used by both above |
| `replay_data.h` | **generated**, not in git. The recording baked into the firmware as a big C array. Made by [`tools/make_replay.py`](../tools/make_replay.py) from a `data/converted/<db>/<record>.npz` ([data notes](data/tpehgdb.md)) | read by [`replay.c`](../firmware/ehg_node/src/replay.c) |

How one frame travels:

```
replay_data.h --(replay.c, 20/s, clock-stamped)--> queue "replay_ring" (256 frames)
  --(ehg_service.c: 10 frames + 20-byte header)--> history copy + Bluetooth message --> laptop (gateway/gateway.py)
laptop --(START / STOP / RESEND)--> ehg_service.c
```

Threads (jobs that run side by side; lower number = more urgent):

| Thread | Priority | Does |
|---|---|---|
| replay thread ([`replay.c`](../firmware/ehg_node/src/replay.c)) | 2 | timing-critical: releases frames on time |
| tx_thread ([`ehg_service.c`](../firmware/ehg_node/src/ehg_service.c)) | 5 | builds and sends packets, handles resends |
| main ([`main.c`](../firmware/ehg_node/src/main.c)) | default | start-up, then prints counters every 10 s |

## Settings (Kconfig, change in prj.conf)

| Setting | Default | Meaning |
|---|---|---|
| `CONFIG_EHG_FRAMES_PER_PACKET` | 10 | frames per packet. More = fewer packets, more waiting (10 = 0.5 s at 20 Hz) |
| `CONFIG_EHG_RING_FRAMES` | 256 | queue size between replay and sender (12.8 s at 20 Hz). Full = frames dropped + counted |
| `CONFIG_EHG_HISTORY_PACKETS` | 256 | sent packets kept for resends (128 s at 20 Hz) |

Sample width (16-bit default, 24-bit option) is not a setting here: it comes from `replay_data.h`
(`make_replay.py --bits 24`).

## The serial log (VCOM0, 115200 baud)

Every 10 s: `sent=… resent=… resend_miss=… notify_err=… ring_overflow=… max_inject_late=… us`

| Counter | Meaning |
|---|---|
| `sent` | packets sent |
| `resent` | packets sent again on request |
| `resend_miss` | resend asked for too late (copy already overwritten) = lost for good |
| `notify_err` | send failed (e.g. laptop connected but not listening yet) |
| `ring_overflow` | frames dropped because the queue was full (sending fell behind) |
| `max_inject_late` | worst lateness of any frame vs its exact due time |

## build/ (generated, not in git)

Made by [`build.sh`](../firmware/build.sh). Safe to delete; the next build remakes it (`build.sh pristine` does a clean build).
Most of it is build-tool internals. The parts worth knowing:

| Item | What |
|---|---|
| `build/ehg_node/zephyr/zephyr.hex` | **the firmware image** that gets flashed onto the board |
| `build/ehg_node/zephyr/zephyr.elf` | same program + debug info (for a debugger) |
| `build/ehg_node/zephyr/zephyr.map` | where every function/variable sits in memory |
| `build/ehg_node/zephyr/.config` | every final setting (Zephyr defaults + prj.conf + Kconfig), e.g. `CONFIG_EHG_FRAMES_PER_PACKET=10` |
| `build/ehg_node/zephyr/zephyr.dts` | the board's hardware description (pins, radio, memory) used for this build |
| `build/ehg_node/zephyr/runners.yaml` | which tool flashes the board (`nrfutil`) |
| `build/ehg_node/compile_commands.json` | lets editors (VS Code) understand the code |
| `build/_sysbuild/`, `build/ehg_node/CMakeFiles/`, `*.ninja`, `CMakeCache.txt`, `modules/` | build-tool internals; ignore |

Last build (16-bit, tpehg1007): 33 % of flash, 28 % of RAM used.

## Glossary

| Term | Meaning |
|---|---|
| Zephyr | small operating system for microcontrollers: threads, timers, Bluetooth stack |
| thread | a job that runs side by side with others |
| queue / ring buffer | fixed-size waiting line between 2 threads |
| tick | 1 step of the board clock: 32768 per second |
| peripheral / central | board = peripheral (advertises, waits); laptop = central (connects) |
| advertising | board broadcasting "I'm here" so the laptop can find it |
| service / characteristic | a named group of data "slots" on the board. Ours: data slot (board → laptop) + command slot (laptop → board) |
| notify | board pushes data to the laptop without being asked each time |
| CCC | switch the laptop flips to say "send me notifications" |
| MTU | biggest message the link allows (247 bytes here) |
| PHY | radio speed mode (2M = 2 Mbit/s) |
| connection interval | how often board and laptop talk (15–30 ms here) |
| prj.conf / Kconfig | build-time settings / our own settings definitions |
| devicetree (`.dts`) | text description of the board's hardware |
| flash | copy the firmware image onto the board |
| west / nrfutil | Nordic's build and flash tools |
