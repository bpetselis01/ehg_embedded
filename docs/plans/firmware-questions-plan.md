# Firmware questions: red errors, INPUT/OUTPUT examples, start-up sequence

**Date:** 2026-10-19
**Mode:** New Feature (lightweight)
**Status:** Plan, not started

## Findings that shape the plan

1. **The red errors are not compile errors.** `firmware/build.sh` builds cleanly on 2026-10-19
   (0 warnings, 0 errors, flash 33 %, RAM 28 %). The red is VS Code C/C++ IntelliSense.
   Cause: every `"file"` in `firmware/ehg_node/build/ehg_node/compile_commands.json` is a
   `/Users/byronpetselis/thesisb/...` path (the build runs through the `~/thesisb` shortcut), but VS Code
   opens `/Users/byronpetselis/Desktop/2026 Term 3/Thesis B/...`. No entry matches, so IntelliSense has no
   Zephyr include paths or `CONFIG_*` defines, and it flags every Zephyr macro (`LOG_MODULE_REGISTER`,
   `K_MSGQ_DEFINE`, `BT_GATT_SERVICE_DEFINE`, ...). `.vscode/settings.json` does not point C/C++ at any
   compile database either. **No `.c` file needs to change for this.**
2. **INPUT/OUTPUT comments live in 17 tracked files, and none of them are `.md` docs:**
   firmware: `main.c`, `replay.c`, `ehg_service.c`, `CMakeLists.txt`;
   gateway: `gateway.py`, `packet.py`, `tracking.py`;
   tools: `convert.py`, `make_replay.py`, `fhir_export.py`;
   backend: `ingest/ingest.py`, `docker-compose.yml`;
   eval: `backend_client.py`, `integrity.py`, `latency.py`;
   viewer: `server.py`, `index.html`.
   Some already contain partial examples (`make_replay.py`, `integrity.py`, `tracking.py`); others only
   describe their inputs and outputs in words.
3. **Correction to "main.c initiates the Bluetooth connection":** the board never starts the connection.
   `main.c` turns Bluetooth on and *advertises* (the peripheral role); the laptop's `gateway/gateway.py`
   (the central role) scans for `EHG-*` and connects. `main.c` then *accepts* the connection and reacts to it in callbacks.
   Streaming starts only when the gateway writes START (`0x01`). The sequence doc must say this.
4. `docs/firmware.md` and `firmware/build.sh` have **uncommitted edits by you**. Keep them, and build on top of them.

## Implementation units

### Unit 1: IntelliSense sees the real paths

**Goal:** VS Code matches open `.c` files to compile commands, so the Zephyr headers and `CONFIG_*` resolve.
**Requirements trace:** R1, R2, R6
**Dependencies:** none
**Files:**
- `firmware/build.sh`: after `west build`, write `$APP/build/compile_commands.json`, a copy of
  `build/ehg_node/compile_commands.json` where **only the `"file":` lines** have `$LINK` replaced by `$REPO`
- `.vscode/settings.json`: add `"C_Cpp.default.compileCommands": "${workspaceFolder}/firmware/ehg_node/build/compile_commands.json"`
- `docs/firmware.md`: one row in the build/ table for the new file

**Approach:** `sed '/"file":/s#'"$LINK"'#'"$REPO"'#' in > out`. Rewrite only `"file"`. The `"command"` string
is split on spaces, so putting the real path (`2026 Term 3/Thesis B`) into the `-I` flags would break them.
`"directory"` and `-I` keep pointing at `~/thesisb`, which exists. The copy lives in `build/`, so it is
gitignored and remade on every build, including pristine builds.
**Patterns:** keep `build.sh`'s one-line-per-step style and its comment header (add step 5b to its numbered list).
**Test scenarios:**
- [ ] Happy: `build.sh` then `grep -c '"file": "/Users/byronpetselis/Desktop' build/compile_commands.json` gives 1 or more, and `grep -c thesisb` on the `"file"` lines gives 0
- [ ] Pristine: `build.sh pristine` still produces the file
- [ ] Build fails (e.g. replay_data.h missing): no stale or half-written copy (`set -e` stops before the sed)
- [ ] Edge: `"command"` strings in the copy are byte-identical to the original (`diff` of non-`file` lines is empty)

**Verification:** reload VS Code, open `main.c` and run *C/C++: Log Diagnostics*. It names the compile_commands entry for `main.c`, and the file shows no red.
**Planning-time unknowns:**
- *Deferred to implementation:* the nRF Connect extension may register itself as the C/C++
  configuration provider and override `compileCommands`. If Log Diagnostics shows it as the provider, also set
  `"C_Cpp.default.configurationProvider": "ms-vscode.cpptools"` in the workspace settings.
- *Deferred:* if any red remains after this, it is a real IntelliSense or GCC difference (e.g. GCC-only
  attributes). Report it file:line before changing any C code.

### Unit 2: Firmware INPUT/OUTPUT examples

**Goal:** each firmware INPUT/OUTPUT shows exactly what it looks like.
**Requirements trace:** R3, R4, R6
**Dependencies:** none
**Files:** `firmware/ehg_node/src/main.c`, `replay.c`, `ehg_service.c`, `firmware/ehg_node/CMakeLists.txt` (comments only)

**Approach:** add `e.g.` lines under each INPUT/OUTPUT, using these sources:
- `main.c` IN: chip ID bytes `... 93 C0` → name `EHG-93C0` (the real DK). OUT: the advert name, and the log lines
  exactly as `LOG_INF` prints them, e.g. `<inf> main: advertising as EHG-93C0`,
  `<inf> main: conn params: interval 30.00 ms, latency 0, timeout 6000 ms`, `<inf> main: ATT MTU: tx 247 rx 247`
  (values from the 2026-10-06 OTA run).
- `replay.c` IN: the first frame row of `replay_data.h` (`1093, 171, -748`). OUT: one `struct ehg_frame`
  `{tick=..., frame_idx=0, s={1093,171,-748}}`, plus the `replay start:` log line.
- `ehg_service.c` IN: the control writes as hex: `01` (START), `02` (STOP), `03 05 00 00 00 02 00`
  (RESEND seq 5, count 2). OUT: one real 80-byte packet as hex, generated by `gateway/packet.py:pack()` from the
  first 10 frames of tpehg1007 and annotated (header | samples), plus the `sent=...` stats line.
- `CMakeLists.txt`: the actual input list and the output path `build/ehg_node/zephyr/zephyr.hex`.

**Patterns:** match the existing header style: short lines, `e.g.` prefix, under 100 columns.
**Test scenarios:**
- [ ] The packet hex decodes with `gateway.packet.parse` back to the stated fields (one-off check in a scratch script)
- [ ] The log-line formats match the `LOG_INF` format strings character for character
- [ ] `firmware/build.sh` still builds, with an unchanged flash/RAM size (only comments changed)

**Verification:** `git diff` touches only comment lines, and the build passes.

### Unit 5: Sequence of events in `docs/firmware.md`

**Goal:** a reader can follow one numbered list from "nothing" to "packets arriving" and on to reconnect.
**Requirements trace:** R5
**Dependencies:** Unit 1 (it mentions the new compile_commands step), Unit 2 (the same log lines)
**Files:** `docs/firmware.md`: new section "## What happens, in order", placed after "src/ (the code)"

**Approach:** one numbered list in 4 stages. Each step has who acts (laptop tool / Nordic / our file:function) and what you see.
1. **Prepare data:** `tools/make_replay.py` → `src/replay_data.h`.
2. **Build:** `build.sh` → `~/thesisb` link → `west build` → CMake runs `CMakeLists.txt`, merges Kconfig +
   `prj.conf` → `.config`, devicetree → GCC compiles our 3 `.c` files + Zephyr → link → `zephyr.hex`
   (+ the compile_commands copy).
3. **Flash + boot:** `build.sh flash` → `west flash` → nrfutil writes `zephyr.hex` over the DK's USB debugger →
   board resets → Zephyr starts the kernel → the `K_THREAD_DEFINE` threads start *before* `main`:
   `replay_thread` blocks on `start_sem`, and `tx_thread` polls `replay_ring` every 10 ms → `main()` runs.
4. **Connect + stream:** `main()`: chip ID → `EHG-93C0` → `bt_enable` → `adv_work_handler` advertises →
   **the gateway scans and connects (the laptop starts the connection)** → `connected()` →
   `ehg_service_set_conn` + PHY/data-length requests → `param_updated`/`phy_updated`/`mtu_updated` log what the laptop
   granted → the gateway subscribes (CCC) and writes `01` → `ctrl_write` → `replay_start` → `replay_thread` releases
   a frame every 50 ms → `tx_thread` packs 10 → `bt_gatt_notify` → the gateway → MQTT. A RESEND loop runs alongside.
   Disconnect → `disconnected()` → `replay_stop` → `recycled()` → advertise again.

Plus one ASCII timeline (board column | laptop column). Link each function to `file:line`.
**Patterns:** the doc's existing plain-language tables and the "How one frame travels" ASCII block. Keep the glossary terms consistent.
**Test scenarios:**
- [ ] Every function named exists (grep each name)
- [ ] Every log line quoted matches a `LOG_INF` format
- [ ] Your uncommitted edits to `firmware.md` are still present (diff shows additions only, in that section)

**Verification:** a cold read from step 1 to the end leaves no "and then what?" gaps; for example, it says who sends START and why threads exist before `main`.

  example that no longer matches the code after a later change. Mitigation: examples come from real runs, and
  Unit 2's packet hex is checked by `packet.parse`. Residual risk accepted: no test enforces comment accuracy.
- **Architecture:** Unit 1's sed touches only `"file"` keys. Rewriting the whole file was rejected because it
  would break `-I` flags on the space in the path.
